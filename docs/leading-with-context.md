# Leading With Context

While working through a job that stores permissions and maps them against
rules, the number of important questions grew quickly. The storage model,
association with agents, dependencies, failure behaviour, and expected scale
all affected the design. Giving someone this work as an implementation
instruction would hide the decisions that actually needed ownership.

Leadership in this situation is not having every answer. It is making the
problem and its boundaries clear enough that another person can find better
answers.

## Explain the Boundaries

Before handing off consequential work, make clear:

- what was observed;
- what outcome is needed;
- which constraints cannot be changed;
- which decisions the owner can make;
- which dependencies or people may block the work; and
- when the work should come back for review.

Do not prescribe an implementation merely because it is the first one I can
imagine. If a particular implementation is required, explain the constraint
that requires it.

Context is not a complete map. Unknowns should remain unknowns rather than
being filled with instructions that only look decisive. Use the distinctions
in [Communication](communication.md) to separate evidence, open questions,
non-goals, and the next resolving action.

## Give Authority With Ownership

Assigning a task without the authority to make its ordinary decisions delegates
execution but retains ownership. Every question returns to the person who made
the assignment, and that person remains the bottleneck.

Name which decisions belong to the owner and which require wider agreement.
Bring the work back for decisions whose cost of being wrong exceeds the
owner's scope, not for every implementation choice.

Trust is not the absence of review. It is agreement about where review is
needed.

## Review the Reasoning

A different approach is not evidence that the work is wrong. Ask whether the
approach accounts for the observed problem, expected scale, failure modes,
dependencies, and the cost of being wrong.

Intervene when evidence or an agreed constraint has been missed. Do not
intervene only because I would have made a different choice.

Responding quickly with my own answer can prevent someone else from developing
a better one. Pause long enough to understand the reasoning before replacing
it. [Working With Restraint](working-with-restraint.md) covers the same pause
before other consequential actions.

## Let Trust Create Capacity

There are only so many decisions one person can make well. If every detail must
return to me, adding people does not add capacity; it adds more work for me to
approve.

Leadership scales when other people have enough context and authority to make
decisions whose consequences they understand. My responsibility moves toward
creating clarity, removing obstacles, sharing knowledge, and helping other
people succeed.

Letting go is not a claim that the work does not matter. It is recognition that
other people are capable of doing work that matters.

## Review Questions

- Does the owner understand the problem, or only the requested implementation?
- Which constraints are real, and have I explained why they exist?
- Which decisions can the owner make without returning to me?
- Am I reviewing evidence and reasoning, or preference?
- What would happen if I did not supply my answer first?
- Have I delegated ownership, or only execution?
